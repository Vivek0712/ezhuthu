# Fine-tuning data for the restoration decider (issue #37)

- Date: 2026-11-02. Builder: `src/ezhuthu/eval/ft_data.py` (tests: `tests/agent/test_ft_data.py`).
- Data (not in git): `/Users/vivekrajaps/tamil-script/ezhuthu-ft/data/` (104 MB). Full sha256s, stats and build
  metadata are in `manifest.json` there (sha256 `2e48462e7277bcfa…`), the live-call ledger in `usage.json`, the
  dropped train items in `dropped_near_duplicates.json`.
- Task: the restorer's decision "which candidate fill (or none) matches the expert restoration".

## What a row is

Every row is the request `Restorer.rank_and_decide` sends, recorded from the restorer itself (a recording decider
stands in for the model; a test checks that the recorded request equals what a real decider receives):

| Shape | Request | Label |
| --- | --- | --- |
| `choice3` | `choice` named `restoration`, `DECIDER_INSTRUCTIONS`, options `c0..c2` (pre-rank top-3, the copy-baseline fill always holds a slot) + `none` | the option whose fill equals the expert target under `metrics.canon` (the scorer of every restoration report), else `none` |
| `noul` | `noul` named `is_restoration`, `NOUL_INSTRUCTIONS`, state + `candidate` (one per top-3 option) | yes if that fill equals the target |

`none` keeps its natural rate (not down-sampled). Each row also carries the reference scores on the same request
(Sonnet self-confidence of each option, pre-rank, LLM probability, sources) so baselines are computed on
identical rows.

Formats (same rows, same order):

| Directory | Schema | Checked with |
| --- | --- | --- |
| `./` | ezhuthu rows: the API payload (`state` + `questions`), label, provenance | `make check` |
| `strands-decider/` | `strands_decider.data.format.Example` + `split` (train/dev/test) + `id` = a decider-lab row | `strands_decider` `read_jsonl`, `decider_lab.rows.check` |
| `sparrow/` | the Example fields only (Sparrow `training/` row format) | Sparrow `training/data.py` `render` |

A dict option is written as indented JSON (what `render_content` does with the dict the restorer sends) and a noul
gets the server's default criteria, so the prompt rendered from every row equals the prompt `strands_decider`
renders for the restorer's own request: 0 mismatches over all 12,934 rows (every set and shape)
(`build_prompt` on both sides, and Sparrow's renderer; script
`/Users/vivekrajaps/tamil-script/ezhuthu-ft/code/validate_formats.py`, run with `~/.venvs/decider-3e94e9d`).

## Candidates

What the deployed restorer would see: retrieval parallels, the copy floor and the character n-gram, plus Sonnet
4.6 (`us.anthropic.claude-sonnet-4-6`, router `sonnet`, no Opus escalation) for the items picked for the LLM.
Ontology hints are off for every split: the ontology is built from the train editions, so for a train item it
can contain that item's own fill.

- TEST: all 413 items with Sonnet (all 413 replies were already in the cache from the PR #31 TEST run: 0 new calls).
- VAL: all 443 items with Sonnet (361 new calls; the rest were cached from the PR #31 VAL runs).
- TRAIN: a seeded sample (seed 13) of 800 items with Sonnet (800 new calls); the other 1,537 have retrieval and
  n-gram candidates only (`candidate_source: retrieval`).
- Live Bedrock calls: **1,162** of the 1,200 budget (hard cap reserved before each call, across runs; `usage.json`).
  142 of them are from a VAL run at 40 rpm that was stopped by hand because the account's Sonnet 4.6 quota is 10
  rpm (throttling); that run's count is reconstructed from its new cache entries (135) plus the 7 items that failed
  after five throttled attempts. Estimated cost at list prices: USD 0.93 (VAL rerun) + 3.26 (TRAIN) logged; the stopped
  run's tokens were not logged (135 replies, roughly USD 0.6 more).

Gap lengths are Tamil letters throughout. The data was generated with the restorer of PR #31 (branch
`team/agent/w3b-eval` at `64edf1c`, exported with `git archive`, unmodified; its length check, copy floor, n-gram
fill length and prompt count letters, and its decider state key is `gap_length_tamil_letters`), plus this

trained on these rows should be served behind the post-#31 restorer (main still sends `gap_length_chars` until

## Leakage

1. Rows come from TRAIN items only; VAL and TEST rows exist for selection (VAL) and one final score (TEST).
2. **Cross-fitted train candidates.** The train corpus has every train fill inline, so retrieval (and the copy
   floor) and the n-gram would read a train item's own answer. Train inscriptions are cut into 5 folds by edition
   group (`same_stone_as`; seed 13) and each item's retrieval index and n-gram model are built without its fold.
   Audit of the written records: 0 of 6,996 train parallels come from the item's own fold or stone.
3. **Formulaic near-duplicates dropped: 96 of 2,433 train items** (78 matched a TEST item, 18 a VAL item):
   - the specified rule, normalised Levenshtein similarity >= 0.9 between 40-letter context windows (20 letters
     each side of the gap, letters only), drops **0**: the closest pairs (for example Rājarāja I's preamble
     `kāntaḷūr-c cālai kalam aṟutta…`) are one formula gapped at different points, which shifts both windows
     (similarity 0.80 to 0.89);
   - so a second, shift-invariant rule is applied too: the train window scores rapidfuzz `partial_ratio` >= 90
     inside a VAL/TEST item's whole context (the hard flag's own measure). It drops the 96.
   - **the partial rule is one-directional** (train window inside the held-out context). The reverse direction (a
     VAL/TEST item's 40-letter window inside a *kept* train item's context, `partial_ratio` >= 90) was measured
     after the build and **not** used to drop rows (`python -m ezhuthu.eval.ft_data audit-dups`; recorded in
     `build_meta.json` `train.reverse_direction`, pairs in `reverse_near_duplicates.json`; `manifest.json` predates
     it and is unchanged, as are all row files and their sha256s):

     | `partial_ratio` >= | kept train items | held-out items (TEST / VAL) | pairs | pairs sharing the target |
     | ---: | ---: | --- | ---: | ---: |
     | 90 | 96 | 39 (33 / 6) | 210 | 1 |
     | 85 | 190 | 72 (55 / 17) | 487 | 8 |
     | 80 | 424 | 118 (78 / 40) | 1,075 | 9 |

     The one same-target pair at 90 is train `DHARMA_INSTiruvavatuturai10101:A.1:4` with TEST
     `DHARMA_INSMelKil00012:1:0`. A future build can drop both directions with `build --symmetric-dups` (rule
     `reverse`), and `build` now records these counts itself.
4. Selection on VAL only; TEST rows are written once and must be scored once.

Residual risks: Sonnet may have seen DHARMA or *South Indian Inscriptions* text in pretraining (as for every LLM
number here); formulae repeated between *train* inscriptions stay in train (they are the legitimate parallels
retrieval uses, and the DATA_CARD measures them through the hard flag).

## How to use (next step)

- Train on `train.*`; pick model, threshold and variant on `val.*`; score `test.*` and `test-bench60.*` once.
- The `none`/positive balance differs by split (VAL has more `none` than TEST, TEST includes the 96 formulaic
  non-hard items); report test-hard next to test.
- Two thirds of the train rows have retrieval-only candidates while VAL/TEST are all Sonnet pools; `candidate_source`
  is on every ezhuthu row if a run wants to weight or filter them.

## Reproduce

```bash
cd <tree with the PR #31 restorer + this builder>   # e.g. ezhuthu-ft/code/w3b-64edf1c
export EZHUTHU_LIVE=1 EZHUTHU_LLM_RPM=9 EZHUTHU_CACHE_DIR=<worktree>/.cache
python -m ezhuthu.eval.ft_data build --out-dir ../../data --split test --llm all
python -m ezhuthu.eval.ft_data build --out-dir ../../data --split val --llm all
python -m ezhuthu.eval.ft_data build --out-dir ../../data --split train --llm 800
python -m ezhuthu.eval.ft_data export --out-dir ../../data \
    --bench-cands eval/reports/2026-11-02-decider-benchmark-candidates.jsonl
```

Records are resumable and every Bedrock reply is cached, so a rerun makes no new calls.
